# 源码精读

目标是让用户**真的懂**，不是读完感觉懂了。核心原则：**讲清楚 WHY，而不只是复述 WHAT**。

判断标准（"四能"）：读完这份分析，用户能不看原代码讲出设计思路 / 能自己实现一个类似的 / 能迁移到别的场景 / 能给别人讲明白。任何一条做不到，说明分析不够深。

## 和其他 skill 的分工

| 用户在干嘛 | 走哪个 |
|---|---|
| 报错、调试、改配置、写代码 | code-answer-style |
| 问"XX 是什么/什么原理"（无具体代码） | concept-explainer |
| 拿着一份具体的代码要吃透 | 本 skill |

本 skill 的写作风格**继承 code-answer-style**：能贴代码不写大段文字、多步流程画 mermaid、不写"之前说的不对"这类修正叙事、不用翻译腔。区别在于本 skill 的 WHY 部分必须展开说（每个 WHY ≥2 句），那不算"用语文复述代码"。

---

## 第 0 步：先把代码真拿到手

**硬规则：没有亲眼读到的代码，一个字都不许写进分析。** 训练记忆里对某个开源库的印象 ≠ 用户手上这份代码。

| 用户给的是 | 怎么拿 |
|---|---|
| 上传的文件 | 读 `/mnt/user-data/uploads/`，二进制/压缩包先解压 |
| GitHub 仓库链接 | sandbox 里下载（白名单含 github.com / codeload.github.com / raw.githubusercontent.com）：<br>`curl -sL -o r.zip https://codeload.github.com/<owner>/<repo>/zip/refs/heads/main && unzip -q r.zip` |
| 粘贴的片段 | 直接用，但要先确认这是不是完整上下文 |

拿到之后先摸清规模，再决定模式：

```bash
find . -type f -name '*.py' -o -name '*.cpp' | head -50
cloc . 2>/dev/null || find . -name '*.py' | xargs wc -l | tail -1
```

关键信息缺失就**先问**，问题要具体到"需要哪个文件/哪个目录"。比如只给了一个类的实现却没有基类定义，就直接说需要哪个文件，不要脑补基类长什么样。

## 模式选择

| 用户意图 | 模式 | 触发词 | 输出载体 |
|---|---|---|---|
| 扫一眼、代码审查 | Quick | "快速看一下"、"这段干嘛的" | 对话内直接答 |
| 学习理解（默认） | Standard ⭐ | "分析一下"、"帮我理解"、"什么原理" | 对话内，按章节结构 |
| 彻底掌握、大项目 | Deep | "彻底分析"、"完全掌握"、"面试准备" | 写成 `.md` 文件 + present_files |

**默认 Standard。** 代码超过 500 行或文件数 > 5，即使用户说"分析一下"也要主动问一句要不要走 Deep。

### Deep 模式在对话环境里怎么跑

没有子 Agent，不能并行。用**分轮递进**代替：

```
第 1 轮：项目地图 + 第 1~3 章  → 写入 xxx-深度分析.md
第 2 轮：第 4~6 章（6 是大头，片段多就再拆轮）→ 追加
第 3 轮：第 7~10 章 → 追加 → present_files
```

每轮结束时在对话里只给一句进度和下一轮要写什么，不要把文件全文复述一遍。写文件用追加，不要每轮重写整个文件。

## 输出骨架

编号必须连续，**禁止**自创 `## Phase N` / `## 阶段N` / `## 模块N` 这类层级打断编号。

```markdown
# [名称] 源码分析

## 理解验证状态          ← 表格：核心概念 × (能自我解释 / 懂WHY / 能迁移)
## 项目地图              ← 文件数 > 5 时才有：目录树 + 入口 + 核心调用链(mermaid)
## 1. 快速概览            语言、规模、类型、核心依赖
## 2. 背景与动机          3 个 WHY
## 3. 核心概念网络        每概念 3 WHY + 关系矩阵 + mermaid 概念图
## 4. 算法与理论          复杂度 + WHY 选它 + 退化场景 + 参考链接
## 5. 设计模式            模式名 + WHY 用 + 不用会怎样
## 6. 关键代码深度解析     6A 片段清单 → 6B 逐片段六节
## 7. 测试用例反向理解     有测试文件时才有
## 8. 应用迁移场景         ≥2 个
## 9. 依赖与使用示例
## 10. 质量验证清单        含四能测试
```

Quick 只出 1、6（简化版：3-5 段核心代码各一句话）、9。
Standard 出 1~6 + 9，第 6 章片段控制在 1-3 个。
Deep 全出。

## 各章的硬要求

### 2. 背景与动机 —— 三个 WHY

1. **WHY 需要这段代码**：解决什么问题，不写会怎样
2. **WHY 选这个方案**：至少列 2 个替代方案 + 为什么没选
3. **WHY 这个场景适用**：适用边界 + 不适用的情况

### 3. 核心概念网络

每个概念回答：是什么 / WHY 需要 / WHY 这样实现 / WHY 不用别的。然后画关系：

| 关系 | 概念 A | 概念 B | WHY 这样关联 |
|---|---|---|---|

孤立的概念列表不算网络图，必须有关系矩阵 + 一张 mermaid 图。

### 4. 算法与理论

时间/空间复杂度 → WHY 选它 → WHY 这个复杂度可接受 → **什么时候会退化** → 权威参考链接。退化场景那条最容易被跳过，不许跳。

### 5. 设计模式

模式名 + 用在哪个类/函数 + WHY 用 + **不用会怎样** + 已知局限（⚠️ 标注）。

### 6A. 核心片段识别

代码 > 500 行或文件 > 5 个时先做筛选，避免"全部浅析"。按优先级挑 3-7 个：

| 优先级 | 类型 | 特征 |
|---|---|---|
| ★★★ | 核心算法 | 复杂逻辑、嵌套循环、位运算 |
| ★★★ | 关键接口/抽象 | 系统边界、被大量调用 |
| ★★☆ | 精妙设计 | 少见的实现方式、有意思的权衡 |
| ★★☆ | 易错点密集区 | 边界处理、并发、内存管理 |
| ★☆☆ | 胶水代码 | 跨模块协调逻辑 |

输出清单表格（编号 / 名称 / `文件:行号` / 优先级 / 为什么选它），并**说明跳过了什么、为什么跳过**。

### 6B. 逐片段六节

每个片段严格按这六节，标题用 `#### N.1` ~ `#### N.6`：

| 节 | 内容 | 最低要求 |
|---|---|---|
| N.1 代码整体作用 | 解决什么问题、在系统里的层次定位、上下游依赖 | ≥150 字 |
| N.2 核心逻辑 | 执行流程图 + 关键数据结构 + 状态变量表 + **≥2 条执行路径**（正常/异常） | ≥200 字 |
| N.3 逐行解释 | **贴真实代码 ≥30 行**，注释标 `// 步骤N:` `// 场景N:` `// 此时 x = ?`，配一个贯穿全程的具体输入值 | ≥300 字 |
| N.4 关键设计点 | 实现选择 / 性能 / 安全健壮性 / 可扩展性 / 潜在问题，每项 ≥2 句 | ≥200 字 |
| N.5 三组示例 | 同一段代码，三组不同输入：基础 / 复杂 / 边界异常，写清执行差异 | ≥150 字 |
| N.6 注意与改进 | ≥2 条注意点（含"不注意会怎样"）+ ≥1 条改进建议 | ≥100 字 |

片段头部带一行：`📍 位置：文件:起止行` / `🎯 优先级：★★★` / `💡 一句话核心：...`

### 7. 测试用例反向理解

测试是最准的使用说明书。检测到 `test_*.py` / `*_test.go` / `*.spec.ts` / `TEST(...)` 等，挑 3-5 个典型用例，重点抓**从测试里才能看出来的边界条件和隐藏行为**。

### 8. 应用迁移

至少 2 个跨领域场景，每个说清：不变的原理是什么 / 要改哪几处（贴代码对比）/ 提炼出的通用模式。这一步是验证理解真伪的，不能写成套话。

### 10. 四能测试

逐条自问自答，任何一条打叉就回去补对应章节，不要写完就交。

## 硬性红线

- 任何一节不许出现"略"、"同上"、"详见上文"、"此处省略"
- 每个 WHY 至少 2 句，禁止单句结论式回答
- 所有代码引用必须带 `文件:行号`，不许凭印象写
- 没验证过的推断必须单独标 `⚠️ 推测，需验证：xxx`，不能和已确认事实混在一起用肯定语气写
- 章节编号连续，不许自创层级
- Deep 模式下每片段六节合计 ≥1000 字，整份文档 ≥8000 字

## 写作要点

1. **先给结论再解释** —— "用 bcrypt 不用 MD5，根本原因是 MD5 太快了"，而不是"由于 bcrypt 具有自适应哈希特性……"
2. **善用类比** —— 锁机制比作图书馆借阅规则，缓存比作把常用东西放桌上
3. **代码注释说意图** —— 注释写"为什么这么干"，不是把代码翻译成中文
4. **顺手标易错点** —— ⚠️ 标常见误区
5. **禁止**："该函数实现了 X 功能"这种读者一眼能看出来的废话、照抄官方文档措辞、大段堆术语不解释

自检：一个刚入行的工程师看得懂吗？有没有让人"哦原来是这样"的地方？
